# 持续世界、区块索引与虚拟拍摄：可行性评估

日期：2026-10-13。性质：研究核对与架构建议，尚未实现以下世界分区功能；没有安装外部扩展、下载权重、启动 UE/Blender 或进行 GPU/媒体验收。既有共享舞台与镜头代码是接入基础，不等于完整世界系统。

## 判断

持续复用建筑/角色/道具，按剧情事件更新状态，多个镜头读取同一场表演时间并换机位，是高可行性的工程方向。LLM 从任意整部小说自动得到完全正确且物理可信的电影，仍不能保证。应先搭可扩充世界骨架，按剧情访问区块逐步细化，而非一次猜测尚未读到的全部世界。

省掉的是每镜重新建模和重新猜位置。每镜仍需要机位/时间窗/角色表演、预演控制渲染、视觉首帧与最终视频推理；复杂动作仍需动作库、骨骼和接触约束。共用世界不代表所有镜头共用同一个初始姿态或同一条全剧时间线。

## 已核对的一手技术

- [StoryBlender 论文](https://arxiv.org/abs/2604.03315)：2026-04-01 初版，2026-10-07 修订；连续性记忆图、统一坐标的标准资产、多智能体与引擎反馈，输出可编辑多镜头 3D 分镜。
- [StoryBlender 项目](https://engineeringai-lab.github.io/StoryBlender/)及[公开代码](https://github.com/EngineeringAI-LAB/StoryBlender)：可参考导演规划、持续资产和引擎校验。README 建议 Blender 4.5 LTS，并提醒 5.0+ 兼容问题；资产与动画依赖配置服务。公开代码不表示已经在本机验证或具备全套本地生成能力，直接复用前还需核对软件与资产授权。
- [SceneCraft](https://arxiv.org/abs/2403.01248)：场景图→数值空间约束→Blender Python→视觉反馈，是另一项可借鉴的实现。
- [LTX Layout to Render](https://docs.ltx.io/open-source-model/vfx-post-production/layout-to-render)及[模型卡](https://huggingface.co/Lightricks/LTX-2.5-22b-IC-LoRA-Layout-To-Render)：接收 Blender/UE 简单白模动画与由同布局首帧制作的美术首帧，适合机位、构图、物体移动引导。需要专用 IC-LoRA、匹配底模和工作流；不能把任意 LTX 图生视频等同于完整白模控制。结果仍需检查几何漂移。
- [LTX IC-LoRA 目录](https://docs.ltx.io/open-source-model/integration-tools/ic-lo-ra-adapters)：Union 的 depth/pose/canny 与 Ingredients 身份/道具参考可作为其他路径。不同适配器的共用与叠加必须由实际后端支持决定，不能直接默认全部一起加载。
- [UE World Partition](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine)：持续关卡、网格单元、按流加载区域，适合后期大型地图。但它本身不理解小说或自动决定导演机位。

## 建议持久结构

| 层 | 保存与职责 |
|---|---|
| World | 世界表现版本、统一坐标/单位、角色身份表、风格与时间规则 |
| Region | 稳定 region_id、别名、世界锚点、局部坐标、边界、门/路/邻接关系、几何版本 |
| Instance | 稳定 instance_id、标准资产 ID、所属区域、米制尺寸、骨骼/碰撞/导航信息 |
| Event/Performance | 当前场戏的事件、状态前提/结果、演员和道具轨道、可复现快照 |
| Coverage/Take | 引用 region 与 performance、机位、焦距、镜头时间到表演时间映射、拍摄版本 |
| Render manifest | 实际消费的区块/实例/事件/模型版本、样本时刻、控制与美术首帧哈希 |

World 中持续布景与某次表演实例分开；重复拍摄相同剧情读取同一快照/轨道，不能不断累加全局状态导致演员在每次重拍时跑到不同位置。故事时间允许回忆、平行事件；镜头播放时间另有映射。世界空间/导航图可以有环，资产生成与缓存依赖才要求无环。

## 索引与增量扩建

双索引：语义索引负责“老宅、祖宅、陈家宅院”等候选检索；空间索引负责边界、视锥、相邻区块、遮挡和路径。地点候选须用小说原文、章节、角色上下文确认 stable ID，不能仅以向量相似度把两个地点合并。

例如 `village/main_street` → 门口 landmark → `tavern/hall` → `tavern/counter`。镜头访问柜台时加载大厅、相关人物道具及机位可见的门外区域。只按演员位置加载会漏掉镜头看见的环境；须覆盖摄像机轨迹/视锥及相关动态实体。

每条世界事实标明 evidence_span、章节、置信度和 source=explicit/inferred/user。未读到后院时记录 unknown，必要预演用明确 provisional 区域。读到新章节输出 WorldDelta，只新增/修正受影响区域；锁定已确认布局。新证据矛盾时提出冲突或新版本，不能移动已经拍摄过的大厅来悄悄迎合新描述。

镜头冻结其实际依赖版本与局部区域集合。新增远处区域不应重算全部已拍镜头；修正相关门位/物体/事件才标记受影响镜头过期。已拍旧版本保留可重放，后续镜头可显式使用新世界版本。

## 编译与拍摄流程

小说/剧集分析 → 事实与候选地点 → 世界增量 → 空间约束求解/引擎校验 → 区块舞台 → 事件与演员调度 → 候选机位与导演目的 → 引擎视锥/遮挡/路线检查 → 镜头白模控制视频 → 匹配布局的美术首帧 → LTX Layout 或后端已支持的结构控制 → 质量验收/剪辑。

LLM 负责提取剧情、目标、动作关系和机位候选；3D 引擎负责数值坐标、尺寸、遮挡、路径、骨骼与已支持的物理约束。走廊“走向门口”须引用门的 landmark 和可达路径，不可凭一句 prompt 决定终点。格斗/抓握/滑雪须经过动作库与接触约束，粗白模不能自动保证脚落地、手握道具或碰撞正确。

多镜头共用相同表演：推门、走到桌旁、坐下只表演一次；门外远景、手部特写与室内反打采样同一条事件轨道。换机位时从新机位取得同一世界时刻的布局与美术首帧，不能把旧机位尾帧原像素直接钉为反打首帧。连续一镜/同机位延续再使用尾帧续接。

## Blender / UE / 本地 LTX 的分工

优先当前 Blender 路线：现有 DirectorScene、SceneProtocol、统一采样、blender_adapter 与控制通道可复用；增加区域组装器与拍摄适配器，避免重做前端和实体体系。标准角色图只提供视觉身份，不能自动当作已有 rigged 3D 人物；白模先采用标定骨骼代理，详细模型另接资产库或生成器。

UE 作为后续渲染后端：需要大型实时漫游、地图加载或更丰富交互时引入 World Partition 与镜头序列。统一世界协议保持引擎无关，Blender 和 UE 是投影/执行后端，不各自持有一份无法同步的剧情事实。坐标轴/单位转换集中到适配器，避免 Blender Z-up、系统 Y-up 和 UE 单位混用。

本轮源码核对：`app/director/renderers/ltx25.py` 有 union payload；本机 `ml-stable-diffusion/ai-studio/cap_api.py` 已有 `control.type=layout` 和专用权重条件分支，其 capability 暴露取决于权重存在。源码还明确 control 与 reference_sheet 不能同次混用。以上均为源码事实，没有检查实际推理效果或证明 Mac MLX 复现官方两阶段流程；接入前应核对 adapter 权重、引导 token、第二阶段条件与帧时间消费。

官方 Layout 的 ComfyUI 路径静音，Python 路径生成新音频，都不会原样保留源音轨。对白、拟音与最终混音仍属独立轨道；不要把白模声轨默认视为已保留。工作流有 8k+1 帧长度规则，必须在拍摄清单中明确原时长/实际输出时长，不容许隐式缩短破坏对白与事件同步。

## 建议执行顺序（新增方案，非交付状态）

1. World/Region/Instance 稳定 ID、双索引、事实来源与 WorldDelta 版本契约。
2. 现有共享舞台扩展为区块实例/地标引用；先用已确认资产或基本几何建一条街、一间酒馆。
3. 同一表演在同一世界中拍门外、手部、室内三镜，证明无需每镜重新建模；人工仍可编辑所有区域/站位/机位。
4. LTX Layout 消费冻结控制包与匹配美术首帧，检查本地后端真正消费条件与时间；Gemini 独立验收，Codex 不擅自启动 GPU。
5. 新章节新增后院：旧区块和镜头版本稳定、仅增量加载/失效局部依赖。
6. 再加入复杂动作、IK、接触、碰撞、UE 后端及更大世界。以真实引擎与媒体证据逐项验收，不把研究效果或数据字段当成已实现能力。
